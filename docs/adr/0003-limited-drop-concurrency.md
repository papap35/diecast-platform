# ADR 0003：限量發售的併發控制：Redis 閘門加條件式扣庫存

- 狀態：採用

## 背景

限量車款開賣的那一秒，上千人同時搶同一件商品的同一列庫存。要求是：絕對不能超賣、售完要快速告知、開賣期間其他頁面不能跟著變慢。

## 決策

兩道防線：

1. **Redis 閘門（減壓）**：以 Lua 腳本原子預扣名額，名額用完的請求直接回應售完，不進資料庫。名額以資料庫庫存初始化，60 秒過期重新同步；Redis 故障時放行。
2. **資料庫（防超賣的最後防線）**：交易內以 `UPDATE ... SET stock = stock - n WHERE stock >= n` 條件式扣庫存，並在同一句 SQL 寫入庫存異動紀錄；多件商品依 id 順序扣，避免死結；扣庫存放在交易最後一步，縮短持有列鎖的時間。同一位會員的結帳以 advisory lock 排隊，限購不會被並發請求繞過。

## 考慮過的替代方案

- **只靠資料庫**：正確但開賣瞬間大量注定失敗的交易在等同一列鎖，售完回應要好幾秒，連線池被占滿，其他頁面跟著變慢。
- **`SELECT ... FOR UPDATE` 先讀再寫**：持鎖時間更長，效能比條件式 UPDATE 差。
- **排隊系統（佇列）**：體驗可控，但架構複雜很多；以目前規模，閘門加資料庫已經足夠。

## 影響

- 以 k6 模擬 1,000 人搶 300 台：14 次測試都剛好成立 300 筆訂單；閘門讓售完回應的中位數從 4.1 秒降到 1.1 秒，每次開賣少了 700 個回滾的交易。數據與過程見[壓力測試報告](../load-testing.md)。
- Redis 名額與資料庫庫存短暫不一致時，最多讓少量請求進入資料庫後失敗，不會超賣。
