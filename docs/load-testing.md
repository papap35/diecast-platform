# 限量發售壓力測試

限量車款開賣的那一秒，是這個平台負載最集中的時刻：上千人同時按下「立即購買」，搶的是同一件商品、同一列庫存。這份報告記錄怎麼模擬這個情境、量到什麼，以及根據數據做的調整。

## 結論

- **不超賣**：這份報告的 14 次測試，每次都是 1,000 人搶 300 台。每次都剛好成立 300 筆訂單，其餘 700 人收到「售完」，沒有任何非預期錯誤。
- **限量閘門把注定買不到的請求擋在資料庫外**：
  - 售完回應的中位數從 4.1 秒降到 1.1 秒。
  - 每次開賣少了 700 個回滾的資料庫交易。
  - 同時間商品頁的 p99 從 3.9 秒降到 1.6 秒。
- **瓶頸會移動**：
  - 只有一個 API 執行個體時，資料庫連線大多在等 Node 送下一句 SQL，瓶頸在 API 端。
  - 擴展到三個執行個體後，瓶頸移到那件商品的庫存列鎖。
  - 把扣庫存縮成一次來回並移到交易最後之後，等鎖的連線變少，三個執行個體時成功結帳的中位數從 2.1 秒降到 1.6 秒。
- **壓測抓到一個真的問題**：第一版在開賣瞬間有 98 個請求回 500。原因是閘門前的資料庫查詢把連線池塞滿（見[壓測抓到的問題](#壓測抓到的問題)）。

## 測試情境

| 項目 | 設定                                                                             |
| ---- | -------------------------------------------------------------------------------- |
| 搶購 | 1,000 位會員在開賣時間同時送出結帳。每人送 1 次、限購 1 台，庫存 300 台          |
| 瀏覽 | 同時間商品頁每秒 100 次請求，持續 70 秒，涵蓋開賣前後                            |
| 驗證 | 成立訂單 = 300、其餘回應 409 售完、非預期錯誤 = 0；資料庫庫存歸零、售出數 = 庫存 |

測試會員直接寫入資料庫，並以 `JWT_SECRET` 簽發 access token。這樣可以省掉註冊時的密碼雜湊，只量測「搶購」本身。

## 測試環境

- 單一台 4 vCPU（Intel Xeon 2.1 GHz）、16 GB 記憶體的雲端開發容器。
- k6 1.3、PostgreSQL 16、Redis 7、Node.js 22，全部跑在同一台機器上，互相搶 CPU。
- API：NestJS + Prisma 7（`@prisma/adapter-pg`），每個執行個體的資料庫連線池 10 條。

> 絕對數字只代表這台機器。正式環境把 API、資料庫與壓測端分開，會快很多。這份報告看的是**同一台機器上不同設計的相對差異**。
>
> 同一組設定重跑，延遲中位數可以差到 ±20%，所以每組至少跑 2～3 次，表格取各次的中位數。

## 執行方式

```bash
cd apps/api
npm run build
# 所有請求都來自同一個 IP，先放寬全域限流
RATE_LIMIT_PER_MINUTE=100000000 node dist/main.js &

# 準備資料 → 取樣資料庫連線 → k6 → 驗證沒有超賣
LABEL=gate-on bash loadtest/run.sh
# 刪除壓測資料
npx tsx loadtest/drop-data.ts cleanup
```

| 檔案                    | 用途                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `loadtest/drop-data.ts` | 準備測試會員與限量商品、驗證沒有超賣、清除資料                                         |
| `loadtest/drop.k6.js`   | k6 腳本：開賣瞬間搶購，同時持續瀏覽商品頁。`API_URLS` 可指定多個執行個體，請求輪流分配 |
| `loadtest/db-waits.ts`  | 從開賣起 6 秒內，每 50ms 取樣一次 `pg_stat_activity`，統計連線在做什麼                 |
| `loadtest/run.sh`       | 串起上面三個步驟，並記錄期間資料庫提交與回滾的交易數                                   |

可調整的環境變數：

| 變數                  | 預設                    | 說明                     |
| --------------------- | ----------------------- | ------------------------ |
| `LOADTEST_MEMBERS`    | 1000                    | 測試會員數               |
| `LOADTEST_STOCK`      | 300                     | 限量商品庫存             |
| `LOADTEST_RELEASE_IN` | 45                      | 準備好資料後幾秒開賣     |
| `BROWSE_RPS`          | 100                     | 商品頁每秒請求數         |
| `BROWSE_DURATION`     | 70s                     | 瀏覽流量持續時間         |
| `API_URLS`            | `http://localhost:4000` | API 位址，多個以逗號分隔 |

對照組用 API 的 `DROP_GATE_ENABLED=false` 關閉限量閘門。

## 結果

延遲單位為毫秒，取各組重複測試的中位數。商品頁的延遲中位數每次都是 3～4ms，p95 也在 10ms 以內，只有開賣那幾秒的 p99 會被拉高，所以表格只列 p99。

### 1. 限量閘門：售完的請求不進資料庫

結帳在進資料庫交易之前，先用 Redis Lua 腳本原子地預扣名額（`DropGateService`）。名額用完的請求只經過 Redis 與記憶體快取，就直接回應售完。

通過閘門的請求，仍然以資料庫的條件式 `UPDATE ... WHERE stock >= 數量` 為準。閘門只負責減壓，防超賣的最後防線還是資料庫。

| 1 個執行個體          | 閘門開啟（3 次）  | 閘門關閉（2 次） |
| --------------------- | ----------------- | ---------------- |
| 成立 / 售完 / 非預期  | 300 / 700 / 0     | 300 / 700 / 0    |
| 售完回應 中位數 / p95 | **1,070** / 2,381 | 4,140 / 4,833    |
| 成功結帳 中位數 / p95 | 2,109 / 2,777     | 2,631 / 3,305    |
| 同時間商品頁 p99      | **1,623**         | 3,931            |
| 回滾的資料庫交易      | **0**             | 700              |

閘門關閉時，700 個注定買不到的請求也要開交易，排隊等同一列庫存的鎖。輪到時才發現庫存是 0，整筆回滾。這段時間它們佔著連線池，連帶拖慢成功的結帳與商品頁。

### 2. 開賣瞬間，資料庫連線在等什麼

`db-waits.ts` 把「忙碌中的連線時間」分成三類：

- **執行 SQL**：資料庫正在跑查詢。
- **等庫存列鎖**：卡在別的交易握著的列鎖。
- **交易中等 API**：交易開著，資料庫已經做完上一句，在等 Node 送下一句 SQL 或 COMMIT。

| 閘門開啟、修改前          | 執行 SQL | 等庫存列鎖 | 交易中等 API |
| ------------------------- | -------- | ---------- | ------------ |
| 1 個執行個體（10 條連線） | 9%       | 33%        | 58%          |
| 3 個執行個體（30 條連線） | 12%      | 54%        | 34%          |

- **1 個執行個體**：連線大部分時間在等 API。上千個請求同時湧入，單一 Node 行程要處理請求驗證、Prisma 查詢編譯、JSON 序列化，來不及送出下一句 SQL。
- **3 個執行個體**：API 端的壓力分散後，瓶頸移到資料庫裡那一列庫存，超過一半的連線時間在排隊等鎖。

扣庫存的 `UPDATE` 會鎖住商品那一列，直到交易 COMMIT。修改前，上鎖之後還要再跑兩趟 API 與資料庫之間的來回：

```text
UPDATE "Product" ... RETURNING "stock"    ← 上鎖
（回到 Node）INSERT INTO "StockMovement"   ← 寫庫存異動紀錄
（回到 Node）COMMIT                        ← 解鎖
```

每一趟來回都要等 Node 的事件迴圈有空。開賣時事件迴圈正忙著處理上千個請求，持鎖時間就被拉長，排在後面的人跟著等。

### 3. 縮短持鎖時間

兩個改動，分別在 `InventoryService.move` 與 `OrdersService.placeOrder`：

1. **扣庫存與異動紀錄合成一句 SQL**：用 data-modifying CTE，一次來回完成 `UPDATE` 與 `INSERT`。
2. **扣庫存移到交易最後**：清購物車等其他寫入都先做，最後才上鎖。從上鎖到 COMMIT 只剩一趟來回。

```sql
WITH updated AS (
  UPDATE "Product" SET "stock" = "stock" + $delta, "updatedAt" = now()
  WHERE "id" = $productId AND "stock" + $delta >= 0
  RETURNING "id", "stock"
), movement AS (
  INSERT INTO "StockMovement" ("id", "productId", "delta", "balance", ...)
  SELECT $id, "id", $delta, "stock", ... FROM updated
)
SELECT "stock" FROM updated
```

順帶修正一個潛在的死結：同一筆訂單（或取消時回補）有多件商品時，改成固定依商品 ID 順序上鎖。兩筆交易同時動到同樣幾件商品時，不會各握一把鎖、互等對方。

| 修改前 → 修改後                    | 1 個執行個體  | 3 個執行個體      |
| ---------------------------------- | ------------- | ----------------- |
| 等庫存列鎖（佔忙碌連線時間）       | 33% → **5%**  | 54% → **38%**     |
| 同時排隊等鎖的連線（最多）         | 8 → 2         | 25 → 14           |
| 成功結帳 中位數                    | 2,191 → 2,109 | 2,135 → **1,623** |
| 成功結帳 p95                       | 2,936 → 2,777 | 2,932 → **2,341** |
| 最後一筆訂單成立（300 台全部售出） | 3,011 → 2,855 | 3,110 → **2,436** |
| 售完回應 中位數                    | 1,228 → 1,070 | 800 → 651         |

- **1 個執行個體**：等鎖幾乎消失，但結帳延遲只在誤差範圍內變化。瓶頸本來就在 Node，省下的等鎖時間變成了等 API。
- **3 個執行個體**：
  - 瓶頸在鎖，改動直接反映在延遲上：成功結帳的中位數少了約 24%，300 台全部售出的時間從 3.1 秒縮短到 2.4 秒。
  - 不過各次測試的範圍有重疊：修改前的中位數介於 1,780～2,227，修改後介於 1,427～2,060。
  - 在這台共用 CPU 的機器上，延遲只能算「有改善的趨勢」。等鎖的比例與排隊連線數下降，才是比較穩定的訊號。

### 4. 水平擴展

修改後的程式，同一台機器上 1 個與 3 個 API 執行個體的比較：

| 修改後、閘門開啟      | 1 個執行個體  | 3 個執行個體  |
| --------------------- | ------------- | ------------- |
| 成功結帳 中位數 / p95 | 2,109 / 2,777 | 1,623 / 2,341 |
| 售完回應 中位數 / p95 | 1,070 / 2,381 | 651 / 1,069   |
| 同時間商品頁 p99      | 1,623         | 974           |
| 資料庫連線總數        | 10            | 30            |

三個執行個體和 k6、PostgreSQL 擠在同樣的 4 顆 CPU 上，還是有明顯改善。限量閘門的名額存在 Redis、各執行個體共用，所以水平擴展不需要額外協調。

## 壓測抓到的問題

第一版跑壓測時，開賣瞬間有 98 個請求回 500：

```text
Transaction API error: Unable to start a transaction in the given time.
```

當時的結帳在進閘門**之前**就先查了兩次資料庫：確認會員狀態、查商品的販售類型。1,000 個請求同時抵達，光這兩個查詢就把 10 條連線佔滿。真正要扣庫存的交易拿不到連線，等超過 Prisma 預設的 2 秒就失敗。

修正內容：

- 商品的販售類型改用 30 秒的記憶體快取。售完的請求從頭到尾不碰資料庫；交易內仍以資料庫最新資料再驗證一次。
- 會員狀態的檢查移到通過閘門之後。
- 結帳交易等待連線的上限放寬到 10 秒（`maxWait`）。

修正後，所有測試都沒有再出現非預期錯誤。

## 解讀

1. **正確性靠資料庫，不靠閘門**：
   - 扣庫存是條件式 `UPDATE`，另有 `CHECK (stock >= 0)` 約束當最後防線，14 次測試都沒有超賣。
   - Redis 閘門故障時直接放行（fail-open），只是失去減壓效果，不會影響正確性。
2. **同一件商品的搶購天生是排隊的**：一列庫存一次只能被一筆交易修改，吞吐量的上限大約是「1 ÷ 持鎖時間」。所以加大連線池沒有用，要縮短持鎖時間。
3. **先量測再優化**：單一執行個體時，等鎖的問題被 API 端的瓶頸蓋住。只看延遲，會以為合併 SQL 沒有用。取樣連線狀態，才看得出瓶頸在哪裡、改動有沒有打中。

## 還能怎麼做（未實作）

| 做法                                                             | 效果                                | 代價                                                      |
| ---------------------------------------------------------------- | ----------------------------------- | --------------------------------------------------------- |
| 庫存分桶：一件商品的庫存拆成 N 列，隨機挑一列扣                  | N 列可以同時上鎖，吞吐量約提高 N 倍 | 剩最後幾台時要掃多列；查詢庫存要加總                      |
| 扣庫存移出互動式交易：單句 `UPDATE` 自動提交，建立訂單失敗再補回 | 持鎖時間只剩 SQL 本身的執行時間     | 失去原子性，需要補償機制與對帳排程                        |
| 以 Redis 為庫存主帳，訂單非同步寫入資料庫                        | 吞吐量最高                          | 要處理 Redis 與資料庫不一致；使用者會看到「排隊中」的狀態 |
| 虛擬排隊室（waiting room）                                       | 把尖峰攤平，API 不必承受瞬間湧入    | 多一層服務，也要另外設計使用者體驗                        |

以這個平台的規模（限量數百台），目前的閘門加條件式扣庫存已經足夠，上表留作流量再大一個數量級時的選項。
